# B-07 — The fixture and the shared Kotlin module

The spec's data: 2,000 items in a bundled JSON fixture of about 1 MB, parsed at launch, and 50
bundled PNG thumbnails. B and C share one Kotlin module byte for byte — kotlinx-serialization,
`StateFlow` — and A does the same work in Swift with `Codable` and `@Observable`.

- **The decision and its reason.** The fixture and the thumbnails are generated by a script with a
  fixed seed and committed with their `sha256`, so every variant parses the same bytes and a reader
  can regenerate them. The digests go into BRIEF.md's pins.
- B1, B2, B3 and C build on **the same** compiled module: the build records the digest of the
  shared module's `.klib` each consumes, and a mismatch fails the build. "The same source" is not the
  same binary if a flag differs. The frameworks differ by design — each bridge produces its own from
  that klib (amendment A1.1) — and their digests are recorded per arm.
- Not covered: UI. The filtering semantics (case, diacritics, which fields) are written once here
  and implemented twice — in Kotlin and in Swift — with one test vector both must pass.

- AC: `fixtures/` (target) holds the JSON, the 50 PNGs and the generator; `sha256` of each in
  BRIEF.md.
- AC: a shared test vector — query → expected item ids — passes against the Kotlin module and
  against A's Swift implementation.
- AC: the four Kotlin arms print the digest of the shared module's klib, and all four are equal;
  each prints its framework's digest beside it.
- Anchors: `fixtures/`, `shared/`, `apps/a-native/` (all target).
